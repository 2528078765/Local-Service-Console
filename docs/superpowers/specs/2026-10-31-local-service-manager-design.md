# 本地服务管理台需求文档

版本：v0.2（已按用户审阅意见修订，进入实现）

日期：2026-10-31

状态：用户已审阅并授权实施；自动扫描及版本区分纳入第一版，技术细节由实现计划确定。
暂定项目名：本地服务管理台 / Local Service Manager。

## 1. 为什么做

电脑上有自己开发的项目，也有下载的本地工具。使用前往往需要找到项目文件夹、想起启动命令、打开终端，然后再找到网页地址。工具多了以后，这些操作难记，也不方便判断哪些服务还在运行。

用户明确提到：每次打开 AutoVid 短视频口播工作台之前，都不容易找到在哪里启动服务。

目标是提供一个固定的网页入口。想用工具时，能在里面找到工具、启动并打开；用完以后，能停止；遇到问题时，能看到原因。

## 2. 已确认内容与文档中的建议

### 2.1 用户已确认

- 管理当前电脑上的本地服务，包括自己开发的项目和下载的工具。
- 用一个网页集中管理，可视化启动和停止服务。
- 首批接入视频转字幕服务，以及 AutoVid 短视频口播工作台。
- 使用 UI UX Pro Max 技能辅助前端界面设计。
- 先把需求文档写清楚，再开展实现。
- 必须有“自动扫描”按钮，按下后自动扫描当前电脑上的本地服务，发现可供本项目管理、打开的工具。
- 同名服务按版本区分；不能把不同版本覆盖成一个条目。
- 用户于本次审阅后授权派发子智能体实施项目；第 2.2 节默认行为沿用为实现基线。
- 开发时使用独立 Git 仓库做版本控制；用户会另行提供 GitHub 仓库地址，完成后按指定地址上传。当前未提供远端，不自行选择仓库。

### 2.2 本稿提出的默认方案

以下是为便于评审提出的建议，不能记作用户已经决定：

- 第一版面向本人在当前 Windows 电脑上使用。
- 通过桌面快捷方式或固定启动文件打开管理台；启动文件自动启动管理后台并打开网页。
- 首次运行不自动设置开机启动，也不自动启动全部业务服务。
- 第一版先支持本地命令、脚本和可执行程序；不要求现有项目迁移到 Docker。
- 关闭网页后，后台与已启动服务继续运行。
- 显式退出管理后台时，默认保留业务服务；下次启动重新核对、恢复管理。
- 服务以中文易记名称展示；目录、命令等放在详情或配置中。
- 以清晰、简洁的工具界面为初始设计方向；配色、主题和布局尚未定稿。

## 3. 成功是什么

1. 用户不需要记住 AutoVid 和字幕工具的目录、命令和端口。
2. 从固定入口打开管理台后，可以找到工具，点击一次“启动并打开”进入它。
3. 可以分清已停止、启动中、运行中、停止中、异常以及外部运行的实例。
4. 启动失败时，能看见可理解的原因，并打开相关日志。
5. 新工具可以通过配置加入，不必为每个工具修改管理台产品代码；复杂工具允许后续增加适配器。
6. 停止或重启一个工具，只影响经核实属于它的进程。
7. 不记得工具装在哪里时，点击“自动扫描”就能找到受支持的工具；能识别出入口的工具可直接从结果启动并打开。
8. 同一工具的不同版本、不同安装位置可以分别看到、分别启动，不因同名而丢失记录。

## 4. 第一版范围

### 4.1 必须交付（P0）

| 编号 | 能力 | 用户得到什么 |
| --- | --- | --- |
| R01 | 固定启动入口 | 桌面快捷方式或固定启动文件启动后台并打开管理网页，重复打开不产生多个后台 |
| R02 | 服务总览 | 看到服务名称、用途、状态、常用操作和实际访问地址 |
| R03 | 启动并打开 | 未运行时先启动，确认可用后打开；已运行时直接打开 |
| R04 | 单独启动、停止、重启 | 可以只开后台而不打开页面，也可以停止或重启指定服务 |
| R05 | 状态与异常识别 | 状态由进程归属、实际监听与健康检查共同决定，不能只根据按钮点击更新 |
| R06 | 日志与错误 | 查看当前/最近一次运行的输出、错误及管理操作记录 |
| R07 | 服务配置管理 | 新增、编辑、停用、移除服务记录；支持配置校验 |
| R08 | 配置与运行记录持久化 | 刷新、关闭网页或重启管理后台后，保留配置并重新核实运行状态 |
| R09 | 首批两个工具接入 | 字幕工具和 AutoVid 使用真实的本地服务流程完成验收 |
| R10 | 本机自动扫描 | 一键后台扫描本机可访问的固定磁盘，自动发现支持的项目、启动入口和运行实例，展示进度、取消及覆盖情况 |
| R11 | 同名工具版本区分 | 显示版本与来源位置；不同安装保留独立条目，重复扫描不重复登记 |

### 4.2 后续再考虑（P1）

- 管理后台随 Windows 登录启动，用户选择的业务服务自动启动。
- 分组、收藏、拖动排序、配置导入导出。
- 一键启动一组服务、多进程项目的依赖顺序编排。
- CPU、内存等资源统计，崩溃通知。
- Docker / WSL / Windows 系统服务等运行方式。

### 4.3 第一版不包含

- 局域网或公网远程控制、多用户登录、权限系统、手机远程使用。
- 自动下载、安装、升级工具，或自动修复它们的运行环境。
- 扫描时执行发现的安装脚本、程序或业务任务；自动扫描只做静态发现，启动由用户点击对应工具触发。
- 整合工具内部的业务页面、模型、素材、字幕任务或口播生成任务。
- 自动提交付费云端生成任务，或集中读取业务工具的 API 密钥。
- 自动重启崩溃服务。第一版显示失败并由用户决定是否重试。

## 5. 用户使用流程

### 5.1 第一次打开

1. 用户通过固定启动入口打开管理台。
2. 后台启动，检查配置与入口端口；浏览器进入服务总览。
3. 总览包含预置的字幕工具和 AutoVid 配置。
4. 检查配置的路径、解释器和脚本是否存在；没有验证通过时显示“配置待修复”，不显示“已就绪”。
5. 用户点击服务的“启动并打开”。

管理台默认只启动自身。服务启动由用户操作触发。

### 5.2 日常使用

1. 打开管理台并找到工具，可按名称/用途搜索，按状态筛选。
2. 已停止的工具：点击“启动并打开”，展示启动反馈；健康检查通过后在新标签页打开业务页面。
3. 已运行的工具：点击“打开”，不重复启动。
4. 启动失败：显示原因、失败时间和“查看日志”“重试”入口，不打开错误地址。
5. 使用完成后，可回到管理台停止服务。

如果浏览器拦截自动打开的新标签页，显示可直接点击的“打开服务”链接，不将弹窗拦截记为服务失败。

### 5.3 添加一个新工具

1. 点击“添加服务”，填写名称、项目目录、启动方式与访问方式。
2. 支持两类启动方式：直接运行程序及其参数；执行用户指定的 PowerShell/CMD/批处理脚本。
3. 简单工具可使用固定地址；会自动选端口的工具需配置地址发现方式或使用适配器。
4. 保存前校验字段；保存成功后显示在列表中，不自动执行。
5. 点击启动后才创建实际进程。

第一版一个服务记录对应一个对外使用的服务入口，可以由启动脚本产生多个子进程。需要多个独立命令、按依赖顺序启动的前后端项目，第一版由用户提供统一启动脚本，管理台暂不做依赖编排。

### 5.4 自动扫描与版本识别（本次审阅新增，P0）

1. 总览提供显著的“自动扫描”按钮。默认枚举当前电脑可访问的固定磁盘，不仅限于项目目录；设置中允许选定或增加扫描目录、排除目录。
2. 扫描异步执行，不阻塞网页启停操作。显示正在扫描的位置、已检查目录数、已发现工具数、跳过/无权访问数和取消按钮，不显示无法计算的百分比。
3. 扫描本地项目清单、受支持的启动脚本和已运行进程的元数据。禁止为了探测而启动程序、安装依赖、执行 package scripts 或导入未知 Python 模块。
4. 已知两个工具必须自动发现；通用发现至少支持 Node 的 `package.json` 服务启动脚本、Python 项目/网页框架入口、明确的 `start`/`启动` 类脚本。Windows 服务/监听进程只作为发现线索，不能直接作为可终止的托管实例。
5. 从静态证据能够确定唯一启动入口和运行环境的结果自动登记，直接提供“启动并打开”。需要补充端口、解释器或选择多个可能入口时，显示“待配置”及缺少的信息，不能把猜测的命令当成可启动结果。
6. 结果展示名称、版本、目录、识别依据和可管理程度。未知版本显示“版本未知”，不得编造。版本优先读取项目自己的 manifest/包元数据或可执行文件版本资源；目录名只能作为带有“推测”说明的备用线索。
7. 不同安装使用规范化的真实目录与入口确定稳定身份，不以名称作为唯一键。同名不同版本独立展示；同名同版本不同目录也保留，附加目录区分。一个安装升级版本时更新其元数据，不制造一条虚假的新安装。
8. 重复扫描增量合并，不覆盖手工修改的启动配置；移走或删除的目录标记“位置失效”，不静默删除登记。已移除的服务再次扫描可重新发现。
9. 默认排除 Windows 系统目录、回收站、系统卷信息、依赖包与环境内部、VCS 对象、已知缓存及本管理台测试/运行目录；不跟随目录联接/符号链接，避免循环与跨目录重复。排除范围在设置/扫描摘要中可见，可由用户调整。
10. 不读取 `.env`、密钥文件或业务素材内容。只分析有限大小的服务声明/启动文件，并处理无权限、损坏清单、长路径和扫描期间目录变化；任何跳过或限制都写入摘要，不能用“全盘扫描完成”掩盖未覆盖区域。
11. 同时最多一次扫描；取消后保留已发现结果并显示“已取消/部分结果”。扫描中断、权限不足或设置了时间/深度限制时显示实际覆盖情况。
12. 任意自定义项目不一定有可推导的启动方式。第一版须真实扫描并给出支持的发现结果和待配置项，不承诺识别所有可执行文件，也不能只返回硬编码的两个工具。

## 6. 页面与交互要求

本节定义信息和行为，不锁定具体视觉稿。

### 6.1 服务总览

- 顶部显示管理后台连接状态、搜索、“自动扫描”和“添加服务”。
- 主区域展示服务卡片或紧凑列表；两种布局由后续视觉稿选择，第一版无需同时实现两种。
- 每个服务显示中文名称、版本、一句用途、文字状态和主操作；同名时通过版本和目录明确区分。
- 运行时展示实际访问地址；详情展示启动时间、运行时长和最近错误。
- 未运行时主操作为“启动并打开”；运行时为“打开”，另有停止、重启。
- 操作进行中显示进度状态并禁用冲突操作；不同服务可独立操作。
- 未添加服务、搜索无结果、后台断连分别有明确提示和下一步入口。

### 6.2 服务详情与日志

- 查看目录、运行方式、访问地址、配置的检查方式及当前运行信息。
- 查看当前运行或最近一次运行的标准输出/错误；已知脚本写入文件时读取指定日志。
- 支持实时追加、暂停滚动和复制当前可见日志。
- 展示操作结果和时间；不在首页展示大段命令行输出。
- 只读取此服务配置指定的日志文件，不提供任意文件读取入口。

### 6.3 新增和编辑

- 常用字段优先，解释器、环境变量、动态地址发现等放在高级设置。
- 字段都有明确标签与示例，错误显示在对应字段附近。
- 运行中的服务禁止修改目录、命令、停止方式、地址发现和健康检查等运行配置；先停止再修改。名称和描述允许修改。
- “停用”表示不允许再启动，不会自动停止正在运行的实例。
- “移除”只删除管理台中的配置和自己的运行记录，不删除项目、素材、环境或业务日志。
- 运行中的服务先停止才能移除；外部运行的只读条目可以移除登记，外部进程保持运行。

### 6.4 设计约束

- 使用已经存在并验证可运行的 UI UX Pro Max 技能辅助设计。
- 界面主要使用中文，不要求用户理解 PID、进程树等概念才能操作。
- 状态必须同时有文字与颜色；按钮有明确文本和键盘焦点。
- 操作反馈及时，不显示无法计算的虚假进度百分比。
- 常用操作以鼠标和键盘均可完成；主要面向电脑浏览器，小窗口下仍能操作且没有页面横向溢出。
- 动效只用于状态反馈，尊重减少动态效果设置。
- 图标按用户规范选用 Iconify；如确需插画使用 unDraw。此类控制台不要求装饰照片或占位图片。
- 配色、浅色/深色主题、组件风格在需求审阅后通过视觉稿确定；不因技能推荐而加入营销首页、试用按钮或无关图表。

## 7. 服务状态与执行规则

### 7.1 状态

| 状态 | 判断与显示规则 |
| --- | --- |
| 检查中 | 后台刚启动或连接恢复，正在核实持久化记录；尚不能按旧记录认定服务运行中 |
| 已停止 | 没有核实到本服务的实例，配置有效 |
| 启动中 | 启动请求已接受，尚未满足可用条件 |
| 运行中 | 核实实例归属、实际入口，健康检查通过 |
| 停止中 | 已请求停止，仍在等待实例退出及入口释放 |
| 异常 | 配置无效、启动失败、托管实例意外退出，或健康检查连续失败；同时显示具体原因 |
| 外部运行 | 确认本工具在外部启动且入口可用，但不属于当前可控制的托管实例 |

“停用”是配置属性，可与以上状态同时显示。后台断开是管理台层面的状态：冻结控制操作，显示最后检查时间；不把所有业务服务误标为已停止。

### 7.2 启动与健康检查

- 每个服务同时最多一个生命周期操作；连续点击、多个标签页同时操作不能产生重复实例。
- 执行前检查目录、程序/脚本和必要字段；不自动下载依赖，不因执行失败擅自切换解释器。
- 对直接命令记录实际进程；对会后台化的脚本记录并核实最终服务进程，脚本退出成功不代表服务已就绪。
- 支持 HTTP 健康检查和纯进程存活检查。网页服务必须至少确认其实际 HTTP 入口可访问。
- 建议默认：启动期限 60 秒、启动时约每秒检查一次；可按工具配置调整。
- 运行中约每 3 秒刷新状态；连续 3 次健康检查失败后标记异常，同时区分进程仍在/已经退出。以上数值是本稿默认建议，可配置。
- 健康检查必须无业务副作用；不能用生成视频、转写字幕等任务作为探活。
- 超时不重启、不重复启动；核实是否仍有本次创建的残留进程，明确提示当前实际情况并提供停止入口。
- 固定端口冲突时提示原因和处理入口，不终止占用者。支持自动换端口的工具按实际地址发现结果处理。

### 7.3 停止、强制停止与重启

- 对运行中的托管服务，停止前显示简短确认：“停止可能中断此工具正在执行的任务”。第一版不承诺能识别工具内部所有任务。
- 首先执行已配置的停止脚本，或使用该运行方式支持的正常退出机制。不能假设所有 Windows 程序都能接收相同退出信号。
- 正常停止建议最多等待 15 秒；超时或不支持正常退出时，说明情况，由用户选择是否“强制停止”。不自动升级成强制终止。
- 停止操作只作用于经核实属于本实例的进程/子进程，不通过进程名称批量杀进程，不仅凭端口号或陈旧 PID 操作。
- 不能核实归属时，显示无法安全控制的原因，保留检查/打开入口；不猜测或扩大终止范围。
- 停止成功需核实目标进程退出、其监听已解除；被其他程序立即占用的端口显示冲突，不继续杀进程。
- 重启必须先确认原实例停止，再启动新实例；停止失败时中止重启。
- 停止本地服务不等于取消已提交的云端任务，界面不能宣称云端任务已停止或费用已终止。

### 7.4 外部实例与重连

- 管理台发现已有监听时，先核实是否为本工具；不能仅凭 HTTP 200 或端口号认领。
- 第一版对未经管理台创建、又无法从可信记录恢复归属的实例，只显示“外部运行”，允许打开，不提供停止或重启。

## 9. 数据与架构要求

### 9.1 服务配置最小字段

| 类别 | 内容 |
| --- | --- |
| 基本信息 | 稳定 ID、名称、版本、版本证据、目录身份、发现来源、说明、是否停用 |
| 运行配置 | 工作目录、程序与参数或脚本路径、脚本解释器、必要环境变量 |
| 访问配置 | 固定 URL 或地址发现方式、预期端口/入口 |
| 状态检查 | HTTP/进程检查类型、超时、检查间隔 |
| 停止配置 | 停止脚本或托管进程停止策略、等待期限 |
| 日志配置 | 捕获输出或指定文件、轮转和大小上限 |

运行信息单独保存，包含实例 ID、创建时间、PID 和进程身份依据、实际地址、操作结果及日志位置。持久化记录只是恢复线索，不能替代现场核实。

### 9.2 实现方向（建议，非已确认技术栈）

- 采用“本机管理后台 + 浏览器前端”，由后台执行进程操作；网页本身不直接控制 Windows 进程。
- 通用执行器负责命令、脚本、日志与状态；少量适配器负责现有工具的特殊运行记录和动态地址。
- 前端框架、后端语言、配置存储选型由实现者在开发计划中提出，需求阶段不锁定。
- 管理台只绑定本机回环地址；业务服务保持原项目独立运行与原访问地址。
- 管理台自身的端口为固定配置，具体默认值在实现时检查本机占用后确定并写入说明。
- 第一版应以当前普通用户身份使用，无需管理员权限；遇到权限不足显示具体问题。
- 配置写入需原子替换，避免中断后丢失整个服务列表；配置损坏时保留原文件并给出恢复方式。
- 运行配置支持 Windows 路径、空格和中文，不通过脆弱的字符串拼接执行程序及参数。

### 9.3 本地控制接口与数据保护

- 启动、停止、编辑等变更操作只接受管理台自己的有效会话请求，校验来源并防止跨站调用；不能因为监听 localhost 就允许任意网页控制进程。
- 不向前端暴露任意命令执行或任意文件读写接口，只能操作已经登记的服务及已验证配置。
- 扫描允许自动登记有静态证据的服务候选；扫描请求本身不能执行候选命令。网页内容、日志内容不能隐式注册服务。真正启动仍需用户对该服务的启动操作。
- 环境变量的敏感值默认隐藏；已有业务工具的密钥不需要导入管理台。不可避免的日志凭据应在管理台展示和复制时脱敏，且不改写原项目日志。
- 管理台运行日志要有限额和轮转。建议每服务保留最近 5 次运行、单文件最多 10 MB；原项目日志的清理由原项目负责。
- 移除服务记录、清理管理台日志不删除业务项目目录或业务文件。
